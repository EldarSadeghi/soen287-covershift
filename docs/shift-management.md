# CS-010: Shift editing and deletion

Issue: https://github.com/EldarSadeghi/soen287-covershift/issues/21
Branch: `codex/CS-010-shift-edit-delete`. Status: user approved push and merge on 2026-11-16.

In the manager Schedule, eligible shifts show Edit shift and Delete shift. Edit opens an inline form prefilled in the business timezone. Managers can change title, worker and start/end dates, including overnight shifts with the next-day end date. Save changes refreshes the schedule. Cancel discards the draft and returns focus to the initiating button. Errors retain the draft. Deletion opens a separate confirmation showing the exact shift, assigned worker, dates/times and a permanent-deletion warning; Cancel is focused by default. Deletion has no undo.

Eligibility policy: only shifts whose original start is still in the future and which have **no linked coverage request of any status** can be edited or deleted. Started/ended shifts cannot be moved into the future to bypass the lock. Open/pending requests and approved/cancelled history remain intact; no requests are silently cancelled, transferred, or erased. Locked schedule cards explain why controls are unavailable. This conservative policy also protects future coverage/history increments. Resolving a coverage request does not unlock the shift while its history remains linked.

The server rechecks the current account, business membership, current start time, coverage links and shift revision inside the same exclusive JSON transaction as the write. Editing shares CS-009 validation for dates, DST ambiguity/gaps, future start, end ordering, same-business worker assignment and overlaps. The edited shift is excluded from its own conflict check. A stale revision returns 409 instead of overwriting a newer edit; a missing/deleted/foreign-business shift returns 404. If another request creates coverage after the page loads, mutation is rejected by the transaction’s fresh coverage check.

`POST /api/manager/shifts/:id/edit` accepts exactly `revision`, `title`, `assignedWorkerId`, `startLocal`, `endLocal`. `POST /api/manager/shifts/:id/delete` accepts only `revision`. Both enforce manager session, exact Origin, JSON, session CSRF, body size and the shared shift-mutation rate limit. The revision is a SHA-256 digest of stored shift fields, returned only through the manager dashboard. It is an optimistic concurrency marker, not an authentication token. No schema migration is needed. Edit preserves ID/createdAt and advances updatedAt; deletion removes only an eligible shift. Other collections remain unchanged.

The manager schedule and counts reload after success. Worker My shifts reflects edits/reassignment/deletion on its next load or Refresh; another open browser tab is not automatically refreshed. Network uncertainty asks the manager to cancel and refresh before retrying. A stale form must be cancelled and reopened from the refreshed schedule.
