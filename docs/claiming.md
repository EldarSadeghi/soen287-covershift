# CS-013: Claim coverage with live conflict detection

Issue: https://github.com/EldarSadeghi/soen287-covershift/issues/27
Branch: `codex/CS-013-claim-conflict-detection`. Status: user approved push and merge on 2026-11-16.

Workers use Open shifts → Check & claim. The loaded board includes only their own assigned-shift and pending-claim commitments. A pure UTC interval check displays overlap warnings inline immediately, without a page reload. Clicking checks that snapshot synchronously, then makes a fresh server preflight request. The server can clear a stale warning or report new conflicts. A successful check opens confirmation; Keep browsing closes it and restores button focus. Preflight is advisory and does not reserve anything.

Confirm claim rechecks everything inside the exclusive JSON transaction, then sets status to pending, claimant to the authenticated worker and updatedAt to a later timestamp. It never changes the shift assignment, original worker or reviewer. The original worker stays responsible until manager approval in CS-014. Claimed requests disappear from the open board; the claimant sees them under My requests → Coverage you claimed. Original owners still see their pending requests and managers see the pending claim in Approvals. No claimant-withdrawal flow is added; the original owner’s existing eligible cancellation is supported.

Conflicts include assigned shifts and other pending claims in the same business whose time ranges truly overlap. Pending claims reserve time for subsequent claim checks even before assignment transfers. Original-worker cancellation releases that reservation while retaining claimant history. Half-open intervals allow one commitment to end exactly when another begins. UTC comparisons handle overnight dates and daylight-saving repeated clock times; local formatted strings are never compared. Existing assigned shifts with an open coverage request still count because that worker remains assigned.

`POST /api/worker/requests/:id/claim-check` accepts exactly `{ revision }`, performs a non-mutating fresh check and returns canClaim, conflicts, own commitments and business timezone. `POST /api/worker/requests/:id/claim` accepts the same body but independently checks eligibility/conflicts inside the write transaction. Both require a current worker session, exact Origin, JSON, session CSRF token, no query selectors, bounded input and the existing 30-change/10-minute coverage limiter. Neither accepts client-supplied claimant, business, time range, status or conflict results.

The request must be open, unclaimed, unreviewed, start in the future and still reference its original assignment in the same business. Workers cannot claim their own requests. Foreign or missing IDs return 404; unavailable, conflicting, expired or stale requests return 409. Revision covers stored request and shift fields, so changes after the board loads require refresh. Final conflict detection uses fresh saved assignments and pending claims even if a preview succeeded earlier. Simultaneous claims on one request yield one claimant; simultaneous overlapping requests claimed by the same worker cannot both succeed. Manager approval must recheck conflicts in CS-014 because managers may change other assignments after a claim.

Open-board commitments and conflict details expose only the signed-in worker’s safe shift fields and whether each is assigned or a pending claim. My requests returns a separate safe claims array scoped to that worker, including retained cancelled/approved claim records; full audit/history remains CS-015. No schema migration or authentication change is needed.

UI includes asynchronous checking/confirmation, inline conflicts, stale/error messages, retry checks, network-uncertainty guidance to refresh before retrying, successful claim refresh, keyboard focus and responsive layouts. A preview may become stale; the server never trusts its prior result. Other open tabs need Refresh.
